# Session 跨设备恢复方案

日期：2026-09-21。状态：调研完成，尚未实施产品改造。本文整合官方资料、本机版本核对和隔离合成测试；涉及判断冲突时，以本文为准。

## 产品决定

Session 替代 FyAgent 的「记忆」一级板块，核心目标是把过去的对话带到另一台设备，并在目标 AI 软件中继续对话。

- **提示词**：可复用的指令模板。
- **Session**：一次实际对话中，用户发送的原文，以及每轮 AI 最终答复原文。
- **记忆**：跨会话的偏好、事实和长期上下文。它不会因界面替换而变成提示词或 Session。

最终答复不做二次摘要，也不是只保存整段会话的最后一条回复。迁移包不包含工具调用、参数、工具结果、终端输出、思考过程、进度播报、附件或工作目录文件；也不通过隐藏备份夹带完整原生日志。用户主动粘贴的文本和最终答复里的代码示例按消息正文保留。

替换入口不自动删除已有 MEMORY.md、USER.md 等用户文件。旧记忆编辑入口的退出和手册调整单独列入实施范围，不把旧记忆转换成会话。

## 推荐恢复路线

采用「统一精简会话记录 → 各软件的原生会话重建」。优先使用官方导入接口，其次使用受支持的会话接口；只有缺少公开接口的软件才研究版本限定的格式适配。

1. 从源软件读取会话，识别真实用户输入及每轮最终答复。
2. 转成 FyAgent 可迁移记录，保存角色、顺序、消息标识、来源软件、原始会话标识、标题、时间及格式版本。
3. 目标设备选择对应软件和本地工作目录；使用目标设备已有登录与模型设置。
4. 适配器把精简记录写入目标软件的原生会话，并记录来源与目标会话的对应关系。
5. 在目标软件打开会话，发送下一条消息，验证能接上历史。

**新设备上的原生会话 ID 可以变化。** 产品需要保留迁移来源，确保历史顺序正确、能连续对话；不能把保留原始 ID 当作跨设备恢复的唯一条件。恢复的是对话上下文，工作文件与尚未完成的工具执行按用户要求不迁移。

“导入成功”“已在目标软件打开”“续聊验证通过”是不同结果。只有可查看、可复制或可以粘贴摘要的来源，不能标为已支持恢复。

## 实测暴露的关键问题

**不能只按 assistant 角色过滤。** Hermes 的现有导入器会带入助手进度和工具名提示。FyAgent 必须按来源区分最终答复、中途播报、工具消息以及运行时注入的上下文；无法确定时报告该来源的识别缺口，不能默默混入。

**目录要逐层映射。** OpenCode 实验中，会话所属目录已被导入器改为目标目录，但助手消息里的路径仍保留模拟的旧 Windows 路径。适配器必须处理恢复元数据里的路径；不任意改写用户消息原文。

**要保存必要结构，而不保存执行内容。** OpenCode 原生导入需要消息 ID、父消息关系、模型等字段。迁移记录应保留合法重建需要的最少元数据，或由目标适配器生成；这些字段不意味着需要迁移工具日志或文件。

**导入要可重复且不覆盖旧会话。** 安装版 OpenCode 源码按 ID 写入，有冲突处理。FyAgent 应建立稳定迁移标识和目标 ID 映射，并区分重复导入与另存副本，不能覆盖目标已有历史。

两项测试均只使用临时合成数据，没有读取真实用户会话，没有调用模型，测试存储已清理。它们证明局部导入和读回可行，尚未证明端到端跨设备恢复。

证据：[OpenCode 实测结果](./opencode-synthetic-result.json)、[Hermes 实测结果](./hermes-synthetic-result.json)、[本机 CLI 核验](./local-cli-evidence.json)、[Codex 协议核验](./codex-protocol-excerpt.json)。OpenCode 适配核对了 [v1.18.30 导入源码](https://github.com/anomalyco/opencode/blob/v1.18.30/packages/opencode/src/cli/cmd/import.ts)，没有混用新版文档的命令。

## 现有产品需要改动的部分

主线已有七个来源的 Session 读取适配器，以及列出会话、读取消息、启动恢复终端等后端命令；这些可复用。现有前端没有完整 Session 页面，通用消息结构也不足以可靠标识轮次和最终答复。现有配置备份不覆盖这些原生会话数据，不能直接作为 Session 迁移方案。

实施需要补齐：最终答复提取、统一迁移格式、导入导出、按版本恢复适配、目录映射、重复导入处理、恢复状态、前端问答列表及详情。当前恢复启动器的跨平台能力也需要验证和补齐。代码基础调查见 [session-feasibility.md](../../.trellis/tasks/09-21-remove-client-projects/research/session-feasibility.md)。

## 实施与验收顺序

先验证 Codex 的公开注入路径和 OpenCode 的完整续聊流程，再验证 Hermes、Gemini，最后攻克缺少明确导入契约的 Claude、Grok、OpenClaw。这个顺序用于尽早验证架构，不把产品永久限定在前几个软件。

每个软件至少通过以下验收，才标记为可恢复：

1. 含多轮问答、工具事件、进度播报和未完成轮次的合成样本，导出后只保留约定内容，包内也不存在隐藏的完整日志。
2. 在目标软件中读回历史，核对角色、文本、顺序和来源标识；没有伪造未完成轮次的答复。
3. 继续发送不重复历史事实的新问题，回复能引用此前合成事实；重启软件后仍能恢复。
4. Mac→Windows、Windows→Mac 各验证一次，覆盖不存在的原目录、重新选择模型与目标账号配置。
5. 重复导入不会重复插入或覆盖已有历史；不支持的版本给出明确结果，失败不伪装成空会话恢复成功。

## 用户操作手册调整

- 用「Sessions：查看、迁移和恢复会话」替换原记忆板块的主流程说明。
- 提示词章节继续说明模板维护；不把聊天输入或长期记忆混进模板功能。
- 增加具体流程：导出 → 另一台设备导入 → 选择本地目录 → 在对应软件继续。
- 清楚说明保留用户原文及每轮最终答复，原生 ID 可能变化，实际文件与工具执行状态不随包迁移。
- 按已通过验收的软件/版本列恢复能力，分别说明未支持、导入失败、缺少软件或目录的处理方式。
- 说明旧记忆文件仍由原软件使用；避免让入口消失被理解为用户长期记忆已经删除。

客户项目删除仍由原 Grok 工作包独立执行；本方案不向其追加 Session 实现范围。

## 对早期研究意见的裁定

早期工作稿提出的“推荐只做查看/复制”“隐藏完整原生状态备份”“继续保留独立记忆一级模块”均未采用，已被用户明确的可恢复目标及内容边界取代。没有公开导入文档表示需要验证，不等于技术上不可能。Codex 的 history.jsonl 也不能当作完整会话 rollout 的替代品。
