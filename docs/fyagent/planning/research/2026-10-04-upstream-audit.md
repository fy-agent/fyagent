## 2. 集成决策边界

项目现行 `.trellis/spec/backend/upstream-sync.md` 要求：来源 tag 核验、显式 two-parent merge、保留上游 ancestry；不能以 squash、rebase、cherry-pick 代替正式 tag 集成。能力表的拆包是产品适配和验收分工，不是让多个执行者各自挑提交。建议一个 source-integration owner 串行负责 stable tag、候选 tag 的来源整合，域 owner 在已固定整合结果上做独立适配。

必须保留 FyAgent 身份/目录/环境变量/协议、当前 schema 26 及迁移链、许可证分界、Windows 安装和单实例边界、WorkBuddy、已有响应式外壳及产品功能。上游 MIT 事实来源与必要署名保留；赞助、推荐、邀请参数、品牌渠道、彩带激励与上游版本营销不迁入产品。

主干审计提供的差异很重要：FyAgent 已有 Codex `source_switch.rs` 的 `patch_source` / `project_source` 和 ChangePlan v2；当前 ChangePlan operation 只有 `CodexProviderSwitch`、`CodexProviderUpsertAndSwitch`、`WorkbuddyModelsSave`。因此 4.0 `live/` 与 `mode/` 的价值是跨客户端扩展、崩溃恢复与归属契约，**不得直接引入第二份 live-state 权威与 ChangePlan 抢写**。本报告中的“优先迁移”是候选建议，最终“已具备/适配/延后”由 FyAgent 主干代码审计合并裁定。

## 5. 数据迁移、回滚与不应直接复制的状态

上游稳定段迁移：v3.20.0 schema16→17 为 `session_usage_dedup`；v3.20.1 17→18 为 `session_log_sync.last_byte_offset/last_tail_fingerprint`；v3.20.4 18→19 为 MiniMax Code 相关应用约束。**FyAgent 已是26**：应审查语义/表列是否已具备，在FyAgent自己的迁移authority中设计后续迁移，不拼版本号或重复建表。

4.0 上游 schema仍19，但以下状态改变很大：

- `live-state.json`：模式、attached、route、contract、聚合成员/key registry、pending operation、Grok写入记录；`codex-catalog-history.json`、`codex-login-stash.json`；`backups/live-first-write/`。全部是设备本地，不跨机同步。
- 旧 `proxy_live_backup` 行首启迁入 `backups/proxy-live-backup/` 后从数据库删除；不能移植这一清理步骤去删 FyAgent 自有恢复记录。
- 旧/新上游版本共用云snapshot而无版本门。旧设备可能删掉新stackModels，新“瘦provider行”被旧程序整份写回会丢全局配置。FyAgent需要独立sync profile/能力版本检查与兼容策略。
- 新引擎退出routing重投影direct，而非还原旧整份备份；Codex官方登录可能存在stash。回滚不仅还原数据库，还须先退出聚合/route、恢复官方登录、退出应用、备份各客户端live文件；旧程序不能识别新状态。需要针对FyAgent编制自己的演练，而非把上游步骤改产品名。
- 切换后的model/effort会归供应商值，用户临时选择不自动回采；通用snippet移除会改变配置归属；这属于需要告知的行为变化。
- 不自动修复历史已丢API key/手写prompt、已覆盖代理参数、已串账户/目录指针、旧0token行/早期重复session行。迁移验收应明确“阻止以后发生”和“修复历史存量”两类范围。

## 7. 可重算证据与覆盖限制

此共享报告保留官方 Release、tag、commit/PR 与 compare 链接，不要求其他设备读取研究者本机附件。重算时从官方仓库核对本报告完整 tag object/peeled SHA，分别枚举 v3.19.2..v3.20.4、v3.20.4..v4.0.0、v4.0.0..a189980f35a4568f8cf3585747895c748b8cec6a 的 git log 和 diff --name-status。
