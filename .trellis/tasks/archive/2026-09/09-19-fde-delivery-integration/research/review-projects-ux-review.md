# 客户项目：产品与交互阶段评审

基线：`26efebed`。只读核对代码、现有 FDE 研究和任务材料；未操作原生界面，未修改产品、未重复测试。布局推断以组件和 CSS 为依据，实际窗口可见范围由主控实看确认。评审期间主控已另派有限重整，本报告不覆盖或接管其实现。

判断：现有能力已能串成项目交付流程，但界面主要按内部模块排列，用户需要自己理解它们的关系。应让用户先知道“这个客户要交付什么、当前能做什么、下次回来从哪里继续”，而非靠更多说明文字补齐。

依据包括当前任务 `prd.md` 的“创建→装配→检查→交接”验收链、`design.md` 的项目业务入口约束，以及既有 `09-16-fde-china-presets/research.md` 对 FDE 从需求界定到实施、交付的定位。该研究属于既有资料，本次没有重新搜索互联网，也未把模板/样例能力当作真实客户交付。

## 三个真实场景

| 场景 | 用户首先要回答的问题 | 当前阻力 | 应有落点 |
| --- | --- | --- | --- |
| 首次创建一个经营周报项目 | 我要为谁做什么，先做哪一步？ | 折叠的新建入口；创建后立即进入大表单；交付方案在长页后方 | 明确新建；项目准备先写目标，也可直接选择经营周报方案；一步完成后指出可选下一步 |
| 日常返回已配置的项目 | 上次用的是什么，哪些变化需要处理？ | 先看名称和说明编辑；包库不显示本项目绑定；资源变化缺少逐项呈现 | 先识别本项目方案和资料，当前异常就地可见；自由切换准备、方案、验证，无强制向导 |
| 接手一个客户交付 | 哪些已经检查、凭什么，谁还欠什么？ | 需穿过配置与包库才能读证据；旧记录与新记录铺开；交接区直接呈现编辑表单 | 直接进入验证交接，先读当前有效结果和待办，再按需展开历史或编辑、导出 |

## 五项高价值问题与最小改法

### 1. 新建入口与首屏未表达任务，所有面板又连续平铺

`src/pages/projects/Page.tsx:144` 把新建客户与项目藏在默认收起的 details；空页只说先加客户或选择项目（220、258）。进入项目后，从项目资料、资源、账号、Codex、使用前检查一路渲染到交付包与验证（459、542、630、701、724、743、748）；`projects.css` 的说明输入至少 230px，名称编辑常驻，标题旁是归档（433）。这套顺序既不是新手开始路径，也不适合每天回来继续交付。

最小改法：采用主控拟定的 **项目准备 / 交付方案 / 验证交接** 三个可自由切换区域；空态有明确“新建项目”入口，新建时可选已有客户或添加客户。名称修改和归档放次级项目设置。项目准备先用一句目标说明，再给“选择交付方案”或“准备工作资料”的明确下一步，不新造工作流引擎，不增加必填流程阶段。保留现有未保存草稿保护，切区不能无提示丢稿。

验收观察：首次打开无需解释即可创建；项目创建后能指出下一步；返回已有项目不必穿过整页编辑表单。

### 2. 包库里的选择不等于项目使用的方案，但界面没有稳定区分

`src/shared/features/delivery-kits-ui/ProjectDeliveryKitsPanel.tsx:66、95` 的选择仅在本次组件内保存，默认取库中第一项；`src/pages/projects/Page.tsx:23` 的面板参数没有传 `project.kit`。项目修订后会重建面板，所以绑定结果提示消失后，展示项不一定就是本项目使用的包。用户还要自行拼出“预览导入→加入库→绑定项目”，同时区分“运行合成样例”和另一面板的“检查本机样本”。另有直接误导：资料未保存时组合层把 projectId 投影成 null（`src/app/ProjectsWorkspace.tsx:100` 附近），包面板311行显示“请先选择项目”，实际已有项目。

最小改法：优先呈现 **本项目使用：包名 + 版本**，以已有 `project.kit` 决定；包库浏览作为选择/更换方案入口。按钮按当前情况表达“预览并加入包库”“用于此项目”“本项目正在使用”，仍保留现有导入与绑定的真实边界。区分“试跑包内样例”与“保存本项目检查”；有未保存资料时就地显示“先保存项目资料”，不要让用户重新选择项目。无需新增包模型或隐式启用工具。

验收观察：绑定第二个包后重开项目，仍准确知道当前使用第二个包；导入并不被误认为已配置客户连接；未保存资料的阻止原因准确。

### 3. “选择资源”缺少使用目的，已有变化状态没有落到具体资源

`Page.tsx:542–626` 将各软件的模型、MCP、Skill、提示词放进一个选择框，主要说明引用“不自动启用”，但没有告诉用户添加后能获得什么。已有引用只显示名称、类型和移除；`DependencySummary`（811起）只统计 missing，drifted/unverifiable 没有逐项呈现。日常返回时，用户无法从“已关联若干项”判断哪一项需要处理。

最小改法：用“本项目要用的工具与资料”表达用途，补一句“记录本项目使用的配置，检查时核对变化，交接时知道采用了什么”。按现有资源种类分组选择；绑定列表直接消费已有依赖快照，逐项显示来源变化、需人工核对或来源删除。编辑入口指向现有对应功能，保留引用与实际启用的区别。模型名的空值应解释沿用何种选择，不能让输入框像无来由的必填设置。

验收观察：改动一个已绑定来源后，回到项目能辨认具体哪项变了及应该去哪里处理；不用翻底层版本或理解内部引用术语。

### 4. 始终禁用的“启动项目 Agent”把可走的 Codex 路径变成了死路

`Page.tsx:701–741` 先生成 Codex 目录、把说明折叠起来，再放一个永久 disabled 的启动按钮。用户容易理解为“项目准备完了，但此功能还不能用”。实际 `src-tauri/src/services/projects/files.rs:214` 已提供独立环境和目录的检查说明，边界是手动在 Codex CLI 继续，而不是完全没有后续。

最小改法：删除不可操作的启动按钮。将准备动作写成“准备 Codex 工作目录”，完成后直接展示“到 Codex 中继续”的明确路径与简短步骤，目录和完整命令可复制/展开；现有原生能力若能安全打开目录则复用，否则以可复制信息完成闭环。账号与工具尚未带入这一条放在步骤旁，不把整段工程验证说明铺成正文。不要为了文案闭环新造自动启动或自动认证。

验收观察：生成完成后，用户知道产物在哪里、如何到 Codex 继续，以及下一步要自行确认什么；界面不暗示点击生成就已启动或连接客户环境。

### 5. 验证交接缺少“接手时先读”的默认状态

`src/shared/features/verification/VerificationPanel.tsx:252–366` 按阶段展开全部历史记录；381起始终渲染交接编辑器，398之后才出现交接预览。对于第一次接手的人，当前有效结果、已过期结果和需要谁继续处理混在编辑动作中。三工作区能解决入口可达性，但仍需避免把交接区变成第二张长表单。

最小改法：在验证交接区先显示每阶段的当前结论与最近检查时间，旧记录收在历史中；交接事项先显示待办和负责人，按“编辑交接事项”进入现有表单。保留机器检查与客户人工验收的区别，不给一个合成总分或“项目已完成”灯。预览/导出作为读完后的主动作；不用新增任务系统、统计页或新持久化状态。此项低于前四项，可由主控按本轮可用时间裁决。

验收观察：接手人能直接说明哪些只是样例、哪些客户已确认、哪些依据过期、未完成事项由谁负责，并找到导出入口。

## 本轮建议边界

优先用现有组件与已有数据完成入口、三工作区、当前绑定、资源状态和 Codex 后续指引；第5项只做默认阅读/展开层次。没有证据要求新增后端能力、状态机、引导弹窗或大篇幅帮助文档。实际视觉比例、交互焦点和小窗口可用性仍由主控在最终界面做原生核验。
