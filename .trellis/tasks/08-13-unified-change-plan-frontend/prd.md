# 统一配置变更前端设计 PRD

## 目标

为 Codex Provider 与 WorkBuddy 配置提供同一套“预览变更 -> 一次确认 -> 执行进度 -> 本机回读结果”体验。首版以 Codex Provider 的新建、编辑、切换跑通纵向链路；WorkBuddy 复用相同体验壳，但保留独立领域表达和后端写入/恢复语义。

## 用户问题

- 当前 Provider 新建、编辑、切换会直接写入，用户无法在副作用发生前确认实际影响。
- 当前 WorkBuddy 保存拥有独立覆盖确认，和未来统一 Change Plan 的一次确认重复。
- “命令返回成功”“配置已写入”“真实使用已观察到”容易被混为一谈。
- 配置在预览后被其他程序修改时，用户需要明确知道旧计划已失效，而不是被要求盲目覆盖。
- 多步写入发生部分失败或恢复失败时，需要给出真实、可继续处理的结果。

## 用户流程

1. 用户在既有 Provider 或 WorkBuddy 表单中编辑配置。
2. 主按钮为“预览变更”，生成不产生写入副作用的 Change Plan。
3. 统一预览层展示目标、变化、风险、重启要求与恢复方式；secret 只显示“已设置/将更新”等脱敏状态。
4. 用户在预览层执行唯一一次“确认并应用”。
5. UI 切换为执行视图，根据后端 job snapshot/event 展示进度，不自行推断成功。
6. 后端完成真实本机回读后，UI 展示结果、警告、partial 或恢复失败。
7. 没有稳定机器使用证据时，明确显示“配置已应用；尚未观察到真实使用”。

## 统一要求

- 两个领域共享预览容器、确认区、步骤进度、结果容器、错误/恢复表达、过期处理和无障碍行为。
- 用户对一次计划只确认一次；WorkBuddy 不再增加覆盖确认。
- 预览后发生 baseline 漂移时，旧计划不可执行，用户只能重新读取并预览。
- 执行期间离开页面后再次进入，能够通过 job snapshot 恢复展示，而不是只依赖组件内存。
- 页面不得根据 mutation resolve、HTTP 200、文件 bytes 变化或缓存刷新自行显示“完成”。
- 真实使用证据与配置应用结果分层；无证据时使用 `not_observed`，不得显示“验证成功”或“可用”。
- 沿用现有设计系统、响应式结构和 i18n，不新增一套视觉语言。

## 领域差异

### Codex Provider

- 首版操作：新建、编辑、切换。
- 预览内容：Provider 名称、操作类型、当前 Provider 路由变化、脱敏凭据状态、live config 影响、可能的重启要求与风险警告。
- “保存 Provider”与“设为当前”必须作为不同操作表达。
- 首版不覆盖 additive Provider、其他 AppType 或主动网络验证。

### WorkBuddy

- 预览内容：规范化 base URL、将新增/更新的模型 ID 摘要、是否清除既有 API Key、配置格式、revision 与备份/恢复方式。
- 不展示 API Key、完整配置文档或不必要的本机路径。
- 模型列表远程获取是用户主动辅助动作，不属于 apply job。
- revision 变化时显示计划已过期并要求重新预览，不提供“仍然覆盖”。

## 非目标

- 不在前端构建通用事务引擎或重型全局状态机。
- 不让 renderer 保存 secret、overwrite token、完整原始配置或恢复材料。
- 不管理 WorkBuddy 账号、登录 token 或登录态。
- 不在 apply 主流程主动联网、获取模型或发送模型请求。
- 不做软件内首任务验证、challenge、runner 或 `user_confirmed` 证据。
- 不把 WorkBuddy 建模为 Provider/AppType。

## 验收标准

- [ ] Codex Provider 新建、编辑、切换均从既有入口进入统一预览，不再直接写入。
- [ ] WorkBuddy 保存进入相同预览和一次确认体验，没有领域专属二次确认。
- [ ] 预览清楚区分“将改变”“不会改变”“风险/重启”“恢复方式”。
- [ ] 执行视图只消费后端 job snapshot/event，刷新或重新进入可恢复显示。
- [ ] 成功、成功但有警告、失败、partial、已恢复、恢复失败、计划过期均有独立 UI 和操作。
- [ ] 配置应用与真实使用证据分开，缺少证据时显示 `not_observed` 的诚实文案。
- [ ] secret、token、完整路径、原始配置不进入 query key、持久缓存、toast 或可复制错误详情。
- [ ] 键盘、焦点、屏幕阅读器、减少动态效果和窄屏场景有明确规范。
- [ ] 复用既有 Dialog/Sheet、Card、Alert、Button、Badge、Progress 等设计系统组件，不引入通用重型前端状态机。
