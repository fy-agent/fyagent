# 统一配置变更产品 PRD

## 1. 文档目的

本 PRD 定义 FyAgent 配置变更的统一产品体验：用户在修改 Codex Provider 或 WorkBuddy 模型配置时，都经过“预览 -> 一次确认 -> 执行 -> 回读”的同一条可理解、可追踪流程。

统一的是用户体验、状态语言和 apply job 的产品合同；各领域仍对自己的配置语义、写入规则和恢复方式负责。首条纵切只覆盖 Codex Provider，WorkBuddy 在共享合同稳定后接入。

## 2. 决策状态

以下内容已经由用户确认，不在后续设计中重新讨论：

- Provider 与 WorkBuddy 共享预览、一次确认、执行、回读体验，能共享的产品能力尽可能共享。
- 首版先跑通 Codex Provider 的新建、编辑和切换。
- WorkBuddy 不增加专属二次确认，也不提供“强制覆盖”。
- 预览后若目标配置被外部修改，原计划失效，用户重新读取并预览。
- apply 主流程只处理本机配置，不主动联网，不发送模型请求。
- 配置成功不等于真实使用成功；没有稳定机器证据时显示 `not_observed` 对应文案。
- 密钥只通过 `secretRef` 和本机 SecretBackend 使用，不建设云端托管或重型密钥产品。

## 3. 用户问题

当前 Provider 操作以“直接保存/切换”为主，WorkBuddy 又有独立的 revision、覆盖 token、备份和原子写机制。用户面临的问题不是缺少更多按钮，而是无法在执行前后清楚回答：

1. 这次会修改什么？
2. 是否会改变当前正在使用的配置？
3. 是否需要重启相关应用？
4. 实际写入是否与预期一致？
5. 失败后系统是否已恢复，还是需要人工处理？
6. “配置已应用”是否意味着模型已经真实可用？

产品需要把这些问题收敛为一套稳定流程，同时避免为了界面统一而混淆不同领域的底层职责。

## 4. 产品目标

### 4.1 用户目标

- 在执行前看懂本次变更及影响。
- 只确认一次，不被底层保护机制反复打断。
- 在执行期间看到真实进度，而不是等待一个无上下文的保存按钮。
- 在执行后知道配置是否已从实际目标回读确认。
- 在发生漂移、失败或恢复失败时得到准确且可行动的结果。
- 不把“写入成功”误解为“模型已真实调用成功”。

### 4.2 产品目标

- 建立可复用的 Change Plan 与本机 apply job 体验合同。
- 以 Codex Provider 新建、编辑、切换验证首条端到端纵切。
- 保持 Provider 与 WorkBuddy 的领域所有权隔离。
- 为 WorkBuddy 后续接入定义无需二次确认的冲突与恢复体验。
- 让后续 Agent 在具备稳定机器观测合同时可以独立补充证据，而不污染 apply 主流程。

### 4.3 成功标准

- 用户可以在执行前理解影响，在执行后区分“已应用”“已恢复”“需要处理”和“真实使用尚未观察到”。
- 前端不根据 mutation 返回、HTTP 状态、重启动作或按钮完成自行推导成功。
- 任一领域底层存在差异时，通过领域 adapter 单列处理，不破坏统一主流程。

## 5. 目标用户与核心场景

### 5.1 目标用户

- 在 FyAgent 中管理本机 Codex Provider 的用户。
- 后续在 FyAgent 中维护 WorkBuddy 自定义模型配置的用户。

### 5.2 首版场景：Codex Provider

- 新建 Provider，但不自动设为当前 Provider，除非用户明确选择该动作。
- 编辑已有 Provider，预览将变化的配置语义。
- 切换当前 Provider，明确展示当前路由变化及可能的重启要求。

### 5.3 后续接入场景：WorkBuddy

- 查看将新增或更新的模型配置摘要。
- 预览后执行本机 `models.json` 变更。
- 外部修改导致基线变化时，使计划失效并要求重新预览。
- 写后回读不一致时由后端自动恢复，并展示恢复结果。

## 6. 统一用户体验

### 6.1 阶段一：编辑

- 用户编辑领域表单。
- 此阶段仅保存前端草稿，不产生配置写入副作用。
- API Key 等 secret value 只存在于完成当前操作所需的最短生命周期内，不进入预览内容、日志或持久化查询缓存。

### 6.2 阶段二：生成预览

- 用户点击“预览变更”。
- 后端读取实际目标的当前基线，生成不可变 Change Plan。
- 预览至少展示：操作类型、语义变化、受影响对象、是否改变当前使用配置、重启要求、风险和恢复方式。
- 预览只展示脱敏信息；secret 只显示引用状态，不显示 secret value。
- 生成预览不得修改业务配置，不得联网探测 Provider 或发送模型请求。

### 6.3 阶段三：一次确认

- 用户针对当前预览确认一次。
- 确认必须绑定具体 plan 与生成时的配置基线，不能复用于其他变更。
- Provider 与 WorkBuddy 均不得在执行中再弹领域专属确认。
- 若执行前发现基线变化，本次确认随计划一起失效，系统返回重新预览入口。

### 6.4 阶段四：执行

- 后端创建可回读的本机 apply job，并再次检查目标基线。
- 前端展示后端提供的 job 状态与步骤，不自行推断执行进度。
- job 调用对应领域 adapter 完成写入；共享层不直接理解 Provider TOML 或 WorkBuddy JSON 的业务细节。
- apply 主流程不得主动联网、获取远程模型列表或发送模型请求。

### 6.5 阶段五：回读与恢复

- 写入后必须从实际目标重新读取，确认结果与已批准计划一致。
- 回读一致时，配置结果可标记为“已应用”。
- 回读失败或不一致时，领域 adapter 按自身能力恢复确认前状态。
- 恢复成功与恢复失败必须分别呈现；不得把 partial 或未知状态显示成成功。
- 无论是否需要恢复，真实使用证据均独立判断。

### 6.6 阶段六：结果

- 结果页保留 job 的最终状态、关键步骤、非敏感错误和下一步操作。
- “配置已应用”仅表示本机目标已回读确认。
- 没有稳定机器观测证据时，显示“配置已应用，尚未观察到真实使用”。
- 重启相关应用是独立动作；发起重启或重启命令成功不等于配置已被真实使用。

## 7. 领域边界与所有权

| 能力 | 共享产品层 | Provider adapter | WorkBuddy adapter |
| --- | --- | --- | --- |
| 编辑草稿 | 统一页面结构与交互规则 | Provider 字段语义 | WorkBuddy 模型字段语义 |
| Change Plan | 身份、基线、过期、脱敏 projection | Provider/current route 变化 | `models.json` 模型变化 |
| 用户确认 | 一次确认及其绑定关系 | 不追加确认 | 不追加确认 |
| apply job | 生命周期、步骤、结果状态、活动记录 | Provider DB 与 Codex live config 写入 | revision、备份、原子文件替换 |
| 回读 | 统一结果要求 | 回读 Provider 和实际 Codex 配置 | 回读实际 `models.json` |
| 恢复 | 统一状态和呈现 | Provider 领域补偿 | 恢复确认前 backup |
| secret | 只传 `secretRef` 与脱敏状态 | 执行时解析所需 secret | 执行时短暂解析并按第三方格式写入 |
| 真实使用证据 | 统一 `not_observed` 表达 | 未来稳定机器观测合同 | 不以人工尝试或首任务作为机器证据 |

### 7.1 必须共享

- “预览 -> 一次确认 -> 执行 -> 回读”的页面骨架。
- Change Plan 的身份、基线绑定、过期和脱敏规则。
- apply job 的状态、步骤、错误、恢复和活动记录表达。
- 计划失效、部分失败、恢复失败与 `not_observed` 的用户文案规则。
- 前端只消费后端 snapshot/event、不自行拼装成功结论的合同。

### 7.2 必须分离

- Provider 的数据库行、current route、应用 live config、add/switch 语义和重启要求。
- WorkBuddy 的 `models.json` schema、revision、重复 ID、备份和原子恢复。
- WorkBuddy 不接收 `AppType`、Provider ID 或通用 Provider mutation。
- `liveConfigChanged` 仅表示 Codex live config 最终 bytes 是否变化，不代表 job 完成或真实使用。
- WorkBuddy 内部 overwrite token 若仍作为写入 capability 存在，只能由后端 job 内部生成和消费，不暴露为第二次用户确认。

## 8. 状态模型与用户文案

### 8.1 Plan 状态

| 状态 | 含义 | 建议文案 | 用户动作 |
| --- | --- | --- | --- |
| `draft` | 表单仍在编辑 | “尚未生成变更预览” | 预览变更 |
| `ready` | 已生成且基线有效 | “请确认以下变更” | 确认并应用 |
| `expired` | 目标配置已变化或计划失效 | “配置已发生变化，请重新预览” | 重新读取并预览 |
| `consumed` | 已用于一次执行 | “此变更计划已执行” | 查看结果或重新编辑 |

### 8.2 Apply job 状态

| 状态 | 含义 | 建议文案 |
| --- | --- | --- |
| `planned` | 已确认，等待执行 | “准备应用配置” |
| `running` | 正在执行或回读 | “正在应用并核对配置” |
| `succeeded` | 写入和真实目标回读一致 | “配置已应用” |
| `warning` | 主要写入成立，但存在需用户关注的非阻断结果 | “配置已应用，但有事项需要注意” |
| `failed` | 未能完成，且旧状态保持或已恢复 | “未能应用配置” |
| `partial` | 部分资源改变且未完全恢复 | “配置只完成了一部分，需要处理” |
| `cancelled` | 执行前取消或安全中止 | “已取消，未继续应用配置” |

### 8.3 恢复状态

| 状态 | 建议文案 |
| --- | --- |
| `not_needed` | 不显示恢复提示 |
| `restored` | “核对未通过，已恢复到变更前状态” |
| `restore_failed` | “自动恢复未完成，请按指引检查本机配置” |

### 8.4 真实使用证据

| 状态 | 含义 | 建议文案 |
| --- | --- | --- |
| `not_observed` | 没有稳定机器证据 | “尚未观察到真实使用” |
| `observed` | 未来由稳定机器合同提供 | “已观察到真实使用” |

首版流程不主动制造 `observed`。人工点击、用户口头确认、HTTP 200、模型列表获取成功、重启成功均不得转换为 `observed`。

## 9. 功能需求

### FR-1：无副作用预览

系统必须基于实际目标当前状态生成预览；生成预览不得写配置、联网探测或发送模型请求。

### FR-2：一次确认

每次 apply 只允许一次用户确认，且确认绑定具体计划和基线。执行阶段不得追加 Provider 或 WorkBuddy 专属确认。

### FR-3：计划漂移处理

确认前或执行前发现实际目标与计划基线不一致时，系统必须使计划失效，不写入、不强制覆盖，并引导用户重新预览。

### FR-4：可见 apply job

执行必须表现为可查询、可回读的本机 job。前端刷新或重新进入页面后，应能获取后端保存的当前结果，而不是只依赖组件内临时状态。

### FR-5：真实目标回读

写入完成后，adapter 必须重新读取实际目标并核对；只有回读一致才能返回 `succeeded`。

### FR-6：准确恢复结果

写入失败或回读不一致时，adapter 必须按领域合同尝试补偿，并分别报告无需恢复、恢复成功、恢复失败和 partial，不得笼统显示“保存失败”。

### FR-7：脱敏与密钥边界

Change Plan、job snapshot、活动记录、错误和前端缓存不得包含 secret value、完整凭据、可逆摘要或不必要的完整本机路径。

### FR-8：证据分层

配置回读、应用重启和真实使用是三个独立结果。没有真实使用机器证据时，系统必须显示 `not_observed`，不得显示 Ready、已验证或等价结论。

### FR-9：Codex 首条纵切

首版必须覆盖 Codex Provider 新建、编辑、切换，并把“保存 Provider”与“设为当前”建模为明确、可预览的不同操作。

### FR-10：WorkBuddy 后续接入

WorkBuddy 必须复用统一流程，并保留其 revision、备份、原子替换和未知字段保护。重复 ID 或外部漂移只能导致计划失效或安全错误，不得触发强制覆盖入口。

## 10. 首版范围

### 10.1 包含

- Codex Provider 新建。
- Codex Provider 编辑。
- Codex Provider 切换当前项。
- 统一 Change Plan 预览。
- 一次确认。
- 可见、可回读的本机 apply job。
- Codex 实际配置回读与准确结果。
- `secretRef` 的脱敏投影。
- 配置已应用但真实使用 `not_observed` 的结果表达。
- 必要时提供独立的 Codex 重启下一步，但不把重启算作 apply 或真实使用成功。

### 10.2 后续接入但本 PRD已定义合同

- WorkBuddy 复用统一流程。
- WorkBuddy 写后回读。
- 回读不一致后的自动恢复。
- WorkBuddy 内部 overwrite capability 的后端化与用户不可见化。

## 11. 非目标

- 不覆盖 additive Provider 或所有 AppType。
- 不建设全产品通用资源事务引擎或重型多资源 Undo 产品。
- 不建设云端密钥托管、团队密钥管理或新的 Vault 产品。
- 不在 apply 主流程主动联网、获取模型列表、探测连通性或发送模型请求。
- 不建设 challenge、runner、逐 Agent CLI 验证 adapter。
- 不建设 WorkBuddy 首任务验证器、UI 自动化或 `user_confirmed` 证据。
- 不管理 WorkBuddy 账号、登录 token 或企业身份。
- 不把 WorkBuddy 建模为通用 Provider。
- 不把 HTTP 200、配置 bytes 变化、重启成功或人工尝试当作真实使用验收。

## 12. 验收标准

### AC-1：统一主流程

给定 Codex Provider 新建、编辑或切换操作，用户必须依次经历预览、一次确认、执行和回读；流程中不存在第二次确认。

### AC-2：计划内容完整且脱敏

预览可识别操作类型、语义变化、是否改变当前配置、重启要求和恢复方式；任何页面、snapshot、活动记录和错误均不出现 secret value。

### AC-3：预览无副作用

仅生成或刷新预览时，Provider 数据、Codex live config 和 WorkBuddy 配置均不发生变化，也不产生远程请求。

### AC-4：外部漂移失效

预览后外部修改目标配置，再执行原计划时，系统返回计划已失效；不写 primary、不写 backup、不提供强制覆盖，只提供重新预览。

### AC-5：执行状态真实

前端展示的阶段和最终结果均来自后端 job snapshot/event。按钮完成、mutation resolved 或缓存刷新不能直接触发成功文案。

### AC-6：写后回读

只有实际目标回读结果与批准计划一致时，job 才能进入 `succeeded`。回读失败、不一致或未知状态不得显示“配置已应用”。

### AC-7：失败和恢复可区分

用户可以区分：未发生写入、失败后已恢复、恢复失败、部分完成。每种状态至少提供一个明确的下一步动作。

### AC-8：证据不越级

配置回读成功后，默认结果为“配置已应用，尚未观察到真实使用”。没有稳定机器观测证据时，不出现 Ready、已验证或真实可用结论。

### AC-9：Provider 与 WorkBuddy 领域隔离

共享合同中不出现 WorkBuddy JSON schema、Provider/AppType 或领域 writer 细节；WorkBuddy adapter 不通过通用 Provider mutation 写配置。

### AC-10：WorkBuddy 无二次确认

WorkBuddy 接入时，重复 ID、revision 漂移或 token 问题均不得产生额外用户确认或强制覆盖按钮；可恢复情况由后端自动处理，不可继续时使计划失效或返回准确失败。

### AC-11：刷新后可回读

在 apply job 已开始或已结束的情况下，用户刷新或重新进入对应页面，仍能读取最新 job 状态与结果；不得因前端组件重建而丢失结论。

### AC-12：首版范围受控

首版演示和验收只要求 Codex Provider 新建、编辑、切换三类操作，不以 additive Provider、其他 Agent、真实模型请求或 WorkBuddy 完整实现作为完成条件。

## 13. 证据边界

### 13.1 可证明“配置已应用”的证据

- apply job 完成了预定写入步骤。
- adapter 从实际目标重新读取。
- 回读结果与批准计划一致。

### 13.2 不能证明“真实使用”的证据

- mutation 返回成功。
- HTTP 200。
- `liveConfigChanged = true`。
- 应用重启命令成功。
- 用户手动尝试或口头确认。
- 模型列表成功获取。
- 测试通过或任务/Issue 状态更新。

### 13.3 工程验收边界

- PRD、UI 原型、后端设计、代码实现和运行时验收是不同交付层。
- PRD 通过只代表需求可执行，不代表功能已实现。
- 代码或测试通过不代表真实桌面运行、用户验收或生产可用。

## 14. 依赖与顺序

1. `#35` 提供 `secretRef + SecretBackend` 边界。
2. `#41/#55` 提供最小 Change Plan、一次确认和可见本机 apply job 合同。
3. `#63` 以 Codex Provider 新建、编辑、切换跑通首条纵切。
4. 共享合同稳定后，`#66` 接入 WorkBuddy，并补写后回读与自动恢复。
5. `#45` 在 WorkBuddy 配置链路上提供官方登录引导和模型接入体验。
6. `#50` 仅提供截图化首次使用与排障文档，不进入机器验证证据。
7. `#51` 仅为具备稳定机器观测合同的 Agent 提供独立证据能力。

完整通用恢复框架不应成为首条 Codex 纵切的前置大门；纵切与最小共享合同应共同校正，再把可复用部分收口。

## 15. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 共享层过厚 | 领域语义泄漏，形成重型事务引擎 | 共享层只拥有流程、状态和脱敏合同，writer/readback/restore 留在 adapter |
| 共享层过薄 | 两套确认、错误和恢复体验继续分叉 | UI 骨架、plan 生命周期、job 状态和证据文案必须统一 |
| 首版范围膨胀 | Codex 纵切被 additive、其他 Agent 和真实验证拖慢 | AC-12 明确首版完成条件 |
| 用户误解成功 | 把配置写入当作真实可用 | 配置结果与 `not_observed` 并列展示，禁止 Ready 文案越级 |
| 外部并发修改 | 覆盖用户或第三方最新配置 | baseline 重检；漂移即失效，不提供强制覆盖 |
| 恢复能力不一致 | UI 承诺超出 adapter 能力 | plan 明示恢复方式；adapter 单列能力，准确返回 partial/restore_failed |
| secret 泄漏 | 凭据进入计划、日志或缓存 | 共享层只看 `secretRef`，所有 projection 和错误统一脱敏 |
| 历史术语残留 | 团队继续实现已冻结方向 | 后续治理清理 Vault、真实请求、challenge、user_confirmed 等 stale references |
